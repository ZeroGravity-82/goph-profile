# GophProfile

GophProfile - микросервис для управления аватарками пользователей.

Пользователь загружает свою фотографию один раз, а внешние платформы, например блоги, форумы и сервисы комментариев, могут запросить его аватарку по email. Если пользователь или готовая аватарка не найдены, сервис возвращает стандартное изображение-заглушку.

Сейчас цель - собрать первый рабочий MVP: REST API, PostgreSQL, MinIO/S3, RabbitMQ, воркер асинхронной обработки и Docker Compose для локального окружения.

## Компоненты системы

- HTTP-сервер на Go с REST API и раздачей web-интерфейса;
- воркер на Go для фоновой обработки изображений и удаления файлов;
- PostgreSQL для пользователей, метаданных аватарок и статусов;
- MinIO/S3 для исходных изображений аватарок и миниатюр;
- RabbitMQ для событий загрузки, обработки и удаления;
- готовый SPA-интерфейс загрузки, адаптированный под модель email -> user_id.

## Технологический стек

- Go 1.21;
- `chi` для HTTP-роутинга;
- PostgreSQL;
- SQL-миграции через `goose` или совместимый инструмент;
- MinIO как S3-совместимое объектное хранилище;
- RabbitMQ для асинхронной обработки;
- Docker и Docker Compose;
- `slog` для логирования;
- `golangci-lint` для статического анализа;
- `go test`, `testify` и `testcontainers-go` для тестов.

## Архитектурные решения

### REST API

Основной интерфейс проекта - REST API. Он подходит для готового SPA и внешних сервисов, которым нужно получать аватарки по HTTP.

### Email и внутренний user_id

`email` и `user_id` не смешиваются.

Внутри сервиса пользователь имеет стабильный UUID:

```text
app_user.id -> avatar.user_id
```

Email используется как публичный атрибут для поиска аватарки внешними сервисами. Такой подход позволяет нормализовать email, искать его без учета регистра и не использовать изменяемый пользовательский атрибут как внутренний ключ владения.

SPA работает так:

1. Пользователь вводит email.
2. SPA вызывает `POST /api/v1/users/resolve`.
3. Сервер находит или создает пользователя и возвращает внутренний UUID.
4. SPA загружает аватарку через `POST /api/v1/avatars` с заголовком `X-User-ID: <uuid>`.

В MVP хранится нормализованный email: `trim + lowercase`. Исходный вариант написания email, введенный пользователем, отдельно не хранится, потому что сейчас сервис не показывает email в пользовательском профиле и не отправляет письма. Если позже появится UX-сценарий, где важно сохранить исходное написание, можно добавить отдельное поле.

### Публичное получение аватарки по email

Главный продуктовый сценарий - получить аватарку по email без знания внутреннего UUID:

```http
GET /api/v1/avatar?email=user@example.com
```

Если пользователь или текущая готовая аватарка не найдены, сервис возвращает стандартную PNG-заглушку. Заглушка хранится как статический ресурс:

```text
web/static/default-avatar.png
```

Текущая аватарка выбирается явно. Для этого у пользователя хранится ссылка на текущую аватарку. Публичная выдача по email возвращает выбранную текущую аватарку, только если она имеет статус `ready` и не удалена. Если текущая аватарка не выбрана, еще обрабатывается или удалена, сервис возвращает стандартную заглушку.

Первая успешно обработанная аватарка пользователя становится текущей автоматически, если у пользователя еще нет выбранной текущей аватарки. Последующие загрузки не меняют текущую аватарку без явного выбора пользователя.

### Хранение файлов

PostgreSQL хранит только пользователей, метаданные, статусы и ключи объектного хранилища. Оригинальные изображения и миниатюры хранятся только в MinIO/S3.

Это снижает размер базы данных, упрощает раздачу бинарных данных и соответствует назначению объектного хранилища.

### Асинхронная обработка

После загрузки исходного файла аватарки сервер сохраняет метаданные и публикует событие в RabbitMQ. Воркер получает событие, читает исходное изображение из MinIO/S3, создает миниатюры и обновляет статус аватарки.

Формы событий берутся из спецификации и будут уточнены при реализации:

```go
type AvatarUploadEvent struct {
    AvatarID string `json:"avatar_id"`
    UserID   string `json:"user_id"`
    S3Key    string `json:"s3_key"`
}

type AvatarProcessEvent struct {
    AvatarID   string         `json:"avatar_id"`
    Operations []ProcessingOp `json:"operations"`
}

type AvatarDeleteEvent struct {
    AvatarID string   `json:"avatar_id"`
    S3Keys   []string `json:"s3_keys"`
}
```

Удаление тоже выполняется в два шага:

1. API делает soft delete в PostgreSQL и возвращает `204 No Content`.
2. Воркер асинхронно удаляет исходное изображение и миниатюры из MinIO/S3.

Операции воркера должны быть идемпотентными: повторная доставка сообщения не должна ломать состояние и не должна приводить к некорректной ошибке, если объект уже удален. Воркер проверяет текущий статус аватарки перед выполнением операции, а временные ошибки обрабатывает retry с backoff.

## Модель данных

Предварительная схема для MVP:

```text
app_user
- id UUID PRIMARY KEY
- email VARCHAR(255) NOT NULL
- current_avatar_id UUID NULL REFERENCES avatar(id)
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL
- deleted_at TIMESTAMPTZ NULL

avatar
- id UUID PRIMARY KEY
- user_id UUID NOT NULL REFERENCES app_user(id) ON DELETE RESTRICT
- file_name VARCHAR(255) NOT NULL
- mime_type VARCHAR(255) NOT NULL
- size_bytes BIGINT NOT NULL
- width INTEGER NULL
- height INTEGER NULL
- original_object_key VARCHAR(512) NOT NULL
- thumb_100_object_key VARCHAR(512) NULL
- thumb_300_object_key VARCHAR(512) NULL
- status avatar_status NOT NULL
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL
- deleted_at TIMESTAMPTZ NULL
```

Из-за взаимной ссылки `app_user.current_avatar_id -> avatar.id` и `avatar.user_id -> app_user.id` миграция может сначала создать `app_user` без `current_avatar_id`, затем создать `avatar`, а после этого добавить `current_avatar_id` через `ALTER TABLE`.

Для активных пользователей нужен уникальный индекс по `lower(email)` в таблице `app_user`, чтобы `User@Example.com` и `user@example.com` считались одним пользователем.

Текущая аватарка должна принадлежать тому же пользователю, быть в статусе `ready` и не иметь `deleted_at`. Этот инвариант проверяется в usecase выбора текущей аватарки; если потребуется жесткая защита на уровне БД, ее можно добавить отдельным ограничением или триггером.

Статус аватарки хранится в PostgreSQL ENUM `avatar_status`:

```sql
CREATE TYPE avatar_status AS ENUM (
    'processing',
    'ready',
    'failed',
    'deleting',
    'deleted'
);
```

Значения:

```text
processing
ready
failed
deleting
deleted
```

## API

Планируемые endpoints MVP:

```http
POST   /api/v1/users/resolve
GET    /api/v1/avatar?email={email}

POST   /api/v1/avatars
GET    /api/v1/avatars/{avatar_id}
GET    /api/v1/avatars/{avatar_id}/metadata
DELETE /api/v1/avatars/{avatar_id}

GET    /api/v1/users/{user_id}/avatar
GET    /api/v1/users/{user_id}/avatars
PUT    /api/v1/users/{user_id}/avatar/current
DELETE /api/v1/users/{user_id}/avatar

GET    /health
GET    /web/upload
POST   /web/upload
GET    /web/gallery/{user_id}
```

### Загрузка аватарки

```http
POST /api/v1/avatars
Content-Type: multipart/form-data
X-User-ID: <uuid>
```

Тело формы:

```text
file: binary image
```

Ограничения:

- максимальный размер файла: 10 МиБ;
- форматы: JPEG, PNG, WebP;
- MIME-тип и содержимое файла должны проверяться на сервере.

Успешный ответ:

```json
{
  "id": "avatar-uuid",
  "user_id": "user-uuid",
  "url": "/api/v1/avatars/avatar-uuid",
  "status": "processing",
  "created_at": "2026-07-14T00:00:00Z"
}
```

Ошибки:

- `400 Bad Request` - некорректный `X-User-ID`, отсутствующий файл или неподдерживаемый формат;
- `413 Payload Too Large` - файл больше 10 МиБ;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Получение аватарки

```http
GET /api/v1/avatars/{avatar_id}?size=300x300&format=webp
```

Параметры:

- `size`: `100x100`, `300x300`, `original`;
- `format`: `jpeg`, `png`, `webp`.

Успешный ответ возвращает бинарные данные изображения и заголовки:

```http
Content-Type: image/jpeg|image/png|image/webp
Cache-Control: max-age=86400
ETag: "<hash>"
```

Если аватарка по ID не найдена, API возвращает `404` с JSON-ошибкой.

### Метаданные аватарки

```http
GET /api/v1/avatars/{avatar_id}/metadata
```

Ответ содержит ID, владельца, имя файла, MIME-тип, размер исходного изображения, размеры изображения, список доступных миниатюр и штампов времени.

### Определение пользователя по email

```http
POST /api/v1/users/resolve
Content-Type: application/json
```

```json
{
  "email": "user@example.com"
}
```

Ответ:

```json
{
  "user_id": "user-uuid",
  "email": "user@example.com"
}
```

### Healthcheck

```http
GET /health
```

Ответ должен быть JSON-объектом с общим статусом сервиса и состоянием зависимостей:

```json
{
  "status": "ok",
  "checks": {
    "postgres": "ok",
    "s3": "ok",
    "rabbitmq": "ok"
  }
}
```

Минимальный набор значений:

- общий `status`: `ok` или `degraded`;
- значения в `checks`: `ok` или `error`.

Если общий статус равен `ok`, API возвращает `200 OK`. Если хотя бы одна зависимость недоступна, тогда общий статус равен `degraded`, и API возвращает `503 Service Unavailable`.

## Модель безопасности MVP

Полноценная аутентификация в MVP не входит.

Текущая модель:

- TLS отвечает за безопасность соединения между клиентами, включая SPA, и сервером;
- `X-User-ID` считается доверенным заголовком текущего MVP;
- сервер валидирует `X-User-ID` как UUID;
- удаление разрешено только владельцу аватарки;
- email валидируется и нормализуется на сервере;
- сервер не возвращает клиенту внутренние ошибки PostgreSQL, MinIO/S3 или RabbitMQ;
- в репозитории не хранятся реальные секреты: пароль PostgreSQL, ключи MinIO, учетные данные RabbitMQ и приватный ключ TLS.

### TLS

Взаимодействие клиентов, включая SPA, и сервера выполняется по защищенному соединению поверх TLS.

TLS защищает транспортный канал между клиентами и сервером. По этому каналу передаются:

- email пользователя при определении внутреннего `user_id`;
- заголовок `X-User-ID`;
- исходный файл аватарки при загрузке;
- бинарные ответы с изображениями;
- JSON-ответы с метаданными аватарок и состоянием сервиса.

TLS не заменяет аутентификацию, проверку владельца аватарки, валидацию `X-User-ID` и проверку загружаемого файла. Он защищает только соединение от чтения и подмены данных между клиентом и сервером.

Для локальной разработки предполагается локальный CA и серверный сертификат, подписанный этим CA. Сервер загружает сертификат и приватный ключ из конфигурации:

```yaml
tls_cert: certs/server.crt
tls_key: certs/server.key
```
Для браузера, который открывает SPA, локальный CA должен быть доверенным в локальном окружении. Иначе браузер покажет предупреждение о недоверенном сертификате.

## Ограничения и мотивация лимитов

- Email ограничен 255 символами, потому что это практический верхний предел адреса и поле используется для ручного ввода и поиска.
- Имя файла ограничено 255 символами, потому что это распространенный верхний предел длины имени файла в файловых
  системах;
- MIME-тип может содержать дополнительные параметры, но на практике редко превышает 50-70 символов, поэтому лимит 255
  символов оставляет запас;
- Размер файла ограничен 10 МиБ, чтобы MVP мог принимать файл одним HTTP-запросом `multipart/form-data` без возобновляемой загрузки частями и отдельной политики длительных операций.
- Ключ объектного хранилища ограничен `VARCHAR(512)`: этого хватает для префиксов, UUID пользователя, UUID аватарки и имени варианта изображения; исходное имя файла в ключ объектного хранилища не включается;
- Миниатюры ограничены размерами `100x100` и `300x300`, потому что этого достаточно для списков, профилей и демонстрации асинхронной обработки.

## Конфигурация

Приложение должно получать настройки из нескольких источников. Приоритет от меньшего к большему:

```text
дефолтное значение < значение из конфигурационного файла < переменная окружения < флаг командной строки
```

Если переменная окружения задана, она считается явным значением даже при пустой строке. Пустое значение обязательного параметра должно приводить к ошибке конфигурации, а не к откату на нижестоящий источник.

В репозитории должны храниться только примеры конфигурации с заглушками вместо секретов. Реальные локальные конфиги, пароли PostgreSQL, ключи MinIO и учетные данные RabbitMQ не коммитятся.

TLS-пути сервера задаются через конфигурацию, переменные окружения или CLI-флаги с тем же приоритетом источников:

```text
tls_cert
tls_key
```

Для локального запуска ожидаемые значения указывают на `certs/server.crt` и `certs/server.key`.

## Локальный запуск

Команды будут уточнены после создания кода, Makefile и compose-файлов.

Ожидаемый локальный сценарий после появления кода и скрипта генерации сертификатов:

```bash
./certs/generate-local-certs.sh
make up
make test
make lint
go run ./cmd/server -c config/server.local.yaml
go run ./cmd/worker -c config/worker.local.yaml
```

Локальная инфраструктура MVP:

- PostgreSQL;
- MinIO;
- RabbitMQ;
- server;
- воркер.

Dockerfile должен быть multi-stage: отдельный build stage на Go-образе и минимальный runtime stage с бинарниками `server` и `worker`. Web-ресурсы копируются в runtime-образ рядом с `server`; их использует только HTTP-сервер для раздачи SPA и `default-avatar.png`.

## Тестирование

Минимальные проверки после реализации:

```bash
go test ./...
golangci-lint run
```

Интеграционные тесты, которым нужны PostgreSQL, MinIO или RabbitMQ, должны запускаться отдельной командой или с build tag `integration`:

```bash
go test -tags=integration ./...
```

Для изолированного тестового окружения используется `testcontainers-go`, если тесту нужен реальный PostgreSQL, MinIO или RabbitMQ.

Целевое покрытие тестами для MVP - больше 50%. Способ расчета покрытия нужно уточнить после появления структуры пакетов.

Приоритет покрытия:

1. usecase-сценарии;
2. HTTP-хендлеры: валидация и маппинг ошибок;
3. репозитории PostgreSQL;
4. адаптеры S3 и RabbitMQ;
5. обработка изображений.
