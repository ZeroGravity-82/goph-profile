# GophProfile

GophProfile - приложение для управления аватарками пользователей, реализованное как микросервис.

Пользователь загружает свою фотографию один раз, а внешние платформы, например блоги, форумы и сервисы комментариев, могут запросить его аватарку по email. Если пользователь или готовая аватарка не найдены, приложение возвращает дефолтное изображение-заглушку.

Сейчас цель - довести первый рабочий MVP до конца: REST API, PostgreSQL, MinIO/S3, RabbitMQ, воркер асинхронной обработки и Docker Compose для локального окружения.

## Компоненты системы

- HTTP-сервер на Go с REST API;
- Nginx для раздачи статических ресурсов SPA и проксирования запросов в HTTP-сервер;

- MinIO/S3 для исходных изображений аватарок и миниатюр;

- воркер фоновой обработки изображений и удаления файлов;

## Архитектурные решения

### REST API

Основной интерфейс проекта - REST API. Он подходит для готового SPA и внешних сервисов, которым нужно получать аватарки по HTTP.

### HTTP-схема приложения

Внешний HTTP-трафик принимает Nginx.

Nginx:

- отдает SPA и статические ресурсы из `web/static`;
- проксирует `/api/*`, `/live`, `/ready` и `/health` в HTTP-сервер;
- отдает дефолтную аватарку по `X-Accel-Redirect`, если HTTP-сервер вернул ссылку на заглушку.

HTTP-сервер обслуживает REST API, проверяет запросы и выполняет сценарии usecase.

### Email и внутренний user_id

`email` и `user_id` не смешиваются.

Внутри приложения пользователь имеет стабильный UUID:

```text
app_user.id -> avatar.user_id
```

Email используется как внешний атрибут для поиска аватарки внешними сервисами. Такой подход позволяет нормализовать email, искать его без учета регистра и не использовать изменяемый пользовательский атрибут как внутренний ключ владения.

SPA работает так:

1. Пользователь вводит email.
2. SPA вызывает `POST /api/v1/users/resolve`.
3. Сервер находит или создает пользователя и возвращает внутренний UUID.
4. SPA загружает аватарку через `POST /api/v1/avatars` с заголовком `X-User-ID: <user_id>`.

В MVP хранится нормализованный email: `trim + lowercase`. Исходный вариант написания email, введенный пользователем, отдельно не хранится, потому что сейчас приложение не показывает email в пользовательском профиле и не отправляет письма. Если позже появится UX-сценарий, где важно сохранить исходное написание, можно добавить отдельное поле.

### Получение аватарки по email

Главный продуктовый сценарий - получить аватарку по email без знания внутреннего UUID:

```http
GET /api/v1/avatar?email=user@example.com
```

Если пользователь или текущая готовая аватарка не найдены, приложение возвращает дефолтную PNG-заглушку. Заглушка хранится как статический ресурс:

```text
web/static/default-avatar.png
```

Текущая аватарка выбирается явно. Для этого у пользователя хранится ссылка на текущую аватарку. Публичная выдача по email возвращает выбранную текущую аватарку, только если она имеет статус `ready` и не удалена. Если текущая аватарка не выбрана, еще обрабатывается или удалена, приложение возвращает дефолтную заглушку.

Первая успешно обработанная аватарка пользователя становится текущей автоматически, если у пользователя еще нет выбранной текущей аватарки. Последующие загрузки не меняют текущую аватарку без явного выбора пользователя.

### Хранение файлов

PostgreSQL хранит только пользователей, метаданные, статусы и ключи объектного хранилища для аватарок. Оригинальные изображения и миниатюры хранятся только в MinIO/S3.

Это снижает размер базы данных, упрощает раздачу бинарных данных и соответствует назначению объектного хранилища.

### Обработка изображений и создание миниатюр

На вход принимаются изображения форматов JPEG, PNG и WebP. HTTP-сервер проверяет размер файла, MIME-тип и базовые ограничения изображения до сохранения исходного файла в MinIO/S3.

Воркер декодирует сохраненный файл, определяет исходные ширину и высоту, вырезает центральную квадратную область и масштабирует ее до размеров `100x100` и `300x300`. Такой подход сохраняет центр кадра и дает одинаковые пропорции миниатюр для горизонтальных, вертикальных и квадратных изображений.

Оригинальный файл сохраняет исходный MIME-тип. Миниатюры всегда кодируются как PNG-файлы, чтобы API мог отдавать их в одном стабильном формате независимо от формата загруженного изображения.

### Асинхронная обработка

После загрузки исходного файла аватарки сервер сохраняет метаданные и публикует сообщение в RabbitMQ. Воркер читает задачу обработки, получает исходное изображение из MinIO/S3, создает PNG-миниатюры `100x100` и `300x300`, сохраняет их в MinIO/S3 и переводит аватарку в статус `ready`.

Если изображение не декодируется, воркер переводит аватарку в статус `failed`. Если временно недоступны PostgreSQL, MinIO/S3 или RabbitMQ, сообщение возвращается в очередь для повторной обработки.

RabbitMQ выбран вместо Kafka, потому что в MVP брокер используется как очередь заданий между компонентами одного приложения: сервер ставит воркеру задачи на обработку изображения или удаление файлов. Здесь важнее подтверждение обработки, повторная доставка и повторные попытки для отдельных заданий, чем долговременный поток сообщений с возможностью повторного воспроизведения.

Параллелизм обработки изображений ограничивается количеством консьюмеров воркера. Это защищает процесс от одновременного декодирования слишком большого числа изображений в память.

Сообщение обработки аватарки содержит:

```go
type AvatarProcessingMessage struct {
    AvatarID          string `json:"avatar_id"`
    UserID            string `json:"user_id"`
    ObjectKeyOriginal string `json:"object_key_original"`
}
```

Сообщение удаления аватарки содержит:

```go
type AvatarDeletionMessage struct {
    AvatarID   string   `json:"avatar_id"`
    ObjectKeys []string `json:"object_keys"`
}
```

Удаление выполняется в два шага:

1. API делает мягкое удаление записи аватарки в PostgreSQL и возвращает `204 No Content`.
2. Воркер асинхронно удаляет исходное изображение и миниатюры из MinIO/S3.

Операции воркера рассчитаны на повторную доставку сообщений: некорректные сообщения отбрасываются, а временные ошибки возвращают сообщение в очередь. Полная политика повторных попыток с задержкой, лимитом попыток и DLQ остается улучшением после MVP.

## Модель данных

Предварительная схема для MVP:

```text
app_user
- id UUID PRIMARY KEY
- email VARCHAR(255) NOT NULL
- current_avatar_id UUID NULL REFERENCES avatar(id)
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL

avatar
- id UUID PRIMARY KEY
- user_id UUID NOT NULL REFERENCES app_user(id) ON DELETE RESTRICT
- file_name VARCHAR(255) NOT NULL
- mime_type VARCHAR(255) NOT NULL
- size_bytes BIGINT NOT NULL
- width INTEGER NULL
- height INTEGER NULL
- original_object_key VARCHAR(512) NOT NULL
- thumb_100_object_key VARCHAR(512) NULL
- thumb_300_object_key VARCHAR(512) NULL
- status avatar_status NOT NULL
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL
- deleted_at TIMESTAMPTZ NULL
```

Для пользователей нужен уникальный индекс по `email` в таблице `app_user`. Email нормализуется до записи, поэтому `User@Example.com` и `user@example.com` сохраняются как одно и то же значение.

Из-за взаимной ссылки `app_user.current_avatar_id -> avatar.id` и `avatar.user_id -> app_user.id` миграция может сначала создать `app_user` без `current_avatar_id`, затем создать `avatar`, а после этого добавить `current_avatar_id` через `ALTER TABLE`. Текущая аватарка должна принадлежать тому же пользователю, быть в статусе `ready` и не иметь `deleted_at`. Этот инвариант проверяется в usecase выбора текущей аватарки без жесткой защиты на уровне БД.

Статус аватарки хранится в PostgreSQL-перечислении `avatar_status`:

```sql
CREATE TYPE avatar_status AS ENUM (
    'processing',
    'ready',
    'failed',
    'deleting',
    'deleted'
);
```

Назначение статусов:

- `processing` - исходный файл уже загружен, воркер еще не завершил обработку;
- `ready` - аватарка обработана, миниатюры созданы, аватарку можно выдавать клиентам;
- `failed` - обработка завершилась ошибкой, аватарку нельзя выбрать текущей;
- `deleting` - запись аватарки мягко удалена, физическое удаление файлов из MinIO/S3 еще выполняется;
- `deleted` - файлы аватарки удалены из MinIO/S3.

## API

Планируемые API-ручки MVP:

```http
# Пользователь и текущая аватарка:
POST   /api/v1/users/resolve
GET    /api/v1/avatar?email={email}
PATCH  /api/v1/avatar
DELETE /api/v1/avatar

# Операции с конкретной аватаркой по ее ID:
POST   /api/v1/avatars
GET    /api/v1/avatars/{avatar_id}
GET    /api/v1/avatars/{avatar_id}/metadata
DELETE /api/v1/avatars/{avatar_id}

# Операции с аватарками через владельца:
GET    /api/v1/users/{user_id}/avatar
GET    /api/v1/users/{user_id}/avatars

# Служебные ручки:
GET    /live
GET    /ready
GET    /health
```

GET-ручки чтения не требуют `X-User-ID`. Заголовок `X-User-ID` требуется только для операций, которые меняют состояние от имени пользователя: загрузка, выбор текущей аватарки и удаление.

### Получение текущей аватарки по email

```http
GET /api/v1/avatar?email=user@example.com
```

Успешный ответ возвращает файл выбранной аватарки.

```http
Content-Type: image/jpeg|image/png|image/webp
Cache-Control: max-age=86400
```

Если пользователь не найден, текущая аватарка не выбрана, еще обрабатывается или удалена, API возвращает `200 OK` с дефолтной PNG-заглушкой `web/static/default-avatar.png`.

Ошибки:

- `400 Bad Request` - некорректный или отсутствующий `email`;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Получение текущей аватарки по ID пользователя

```http
GET /api/v1/users/{user_id}/avatar
```

Успешный ответ возвращает файл выбранной аватарки.

```http
Content-Type: image/jpeg|image/png|image/webp
Cache-Control: max-age=86400
```

Если пользователь не найден, текущая аватарка не выбрана, еще обрабатывается или удалена, API возвращает `200 OK` с дефолтной PNG-заглушкой `web/static/default-avatar.png`.

Ошибки:

- `400 Bad Request` - некорректный `user_id`;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Загрузка аватарки

```http
POST /api/v1/avatars
Content-Type: multipart/form-data
X-User-ID: user-id
```

Тело формы:

```text
file: binary image
```

Ограничения:

- максимальный размер файла: 10 МиБ;
- максимальная длина имени файла: 255 байт;
- форматы: JPEG, PNG, WebP;
- MIME-тип и содержимое файла должны проверяться на сервере.

Успешный ответ:

Ответ содержит ID созданной аватарки, владельца, URL для получения аватарки, статус обработки и момент создания записи.

```json
{
  "id": "avatar-id",
  "user_id": "user-id",
  "url": "/api/v1/avatars/avatar-id",
  "status": "processing",
  "created_at": "2026-07-14T00:00:00Z"
}
```

Ошибки:

- `400 Bad Request` - некорректный `X-User-ID`, отсутствующий файл, слишком длинное имя файла или неподдерживаемый формат;
- `413 Payload Too Large` - файл больше 10 МиБ;
- `415 Unsupported Media Type` - `Content-Type` не `multipart/form-data`;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Получение аватарки

```http
GET /api/v1/avatars/{avatar_id}?size=300x300&format=png
```

Параметры:

- `size`: `100x100`, `300x300`, `original`;
- `format`: `jpeg`, `png`, `webp`.

Параметр `format` не выполняет конвертацию. Если он задан, запрошенный формат должен совпадать с фактическим форматом возвращаемого объекта. Если формат не совпадает с выбранным объектом, API возвращает `400 Bad Request`. Оригинал сохраняет исходный MIME-тип, миниатюры MVP отдаются как PNG.

Успешный ответ возвращает бинарные данные изображения и заголовки:

```http
Content-Type: image/jpeg|image/png|image/webp
Cache-Control: max-age=86400
```

Если аватарка по ID не найдена, API возвращает `404` с JSON-ошибкой.

### Метаданные аватарки

```http
GET /api/v1/avatars/{avatar_id}/metadata
```

Ответ содержит ID, владельца, имя файла, MIME-тип, размер файла в байтах, размер изображения в пикселях, список доступных миниатюр, моменты создания и обновления аватарки.

Пример ответа:

```json
{
  "id": "avatar-id",
  "user_id": "user-id",
  "file_name": "avatar.jpg",
  "mime_type": "image/jpeg",
  "size_bytes": 1024000,
  "width": 1920,
  "height": 1080,
  "status": "ready",
  "thumbnails": [
    {
      "size": "100x100",
      "url": "/api/v1/avatars/avatar-id?size=100x100"
    },
    {
      "size": "300x300",
      "url": "/api/v1/avatars/avatar-id?size=300x300"
    }
  ],
  "created_at": "2026-07-14T00:00:00Z",
  "updated_at": "2026-07-14T00:00:05Z"
}
```

Ошибки:

- `400 Bad Request` - некорректный `avatar_id`;
- `404 Not Found` - аватарка не найдена;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Список аватарок пользователя

```http
GET /api/v1/users/{user_id}/avatars
```

Ручка возвращает аватарки пользователя: готовые, обрабатываемые и завершившиеся ошибкой обработки.

Ответ содержит массив аватарок с URL получения файла, метаданными, статусом обработки и признаком текущей выбранной аватарки.

Пример ответа:

```json
{
  "avatars": [
    {
      "id": "avatar-id",
      "user_id": "user-id",
      "url": "/api/v1/avatars/avatar-id",
      "file_name": "avatar.jpg",
      "mime_type": "image/jpeg",
      "size_bytes": 1024000,
      "width": 1920,
      "height": 1080,
      "status": "ready",
      "is_current": true,
      "created_at": "2026-07-14T00:00:00Z",
      "updated_at": "2026-07-14T00:00:05Z"
    }
  ]
}
```

Ошибки:

- `400 Bad Request` - некорректный `user_id`;
- `404 Not Found` - пользователь не найден;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Выбор текущей аватарки

```http
PATCH /api/v1/avatar
Content-Type: application/json
X-User-ID: user-id
```

Тело запроса:

```json
{
  "avatar_id": "avatar-id"
}
```

Ручка выбирает готовую аватарку пользователя как текущую. Пользователь определяется по `X-User-ID`. Выбранная аватарка должна принадлежать этому пользователю, иметь статус `ready` и не иметь `deleted_at`.

Успешный ответ:

```http
204 No Content
```

Ошибки:

- `400 Bad Request` - некорректный `X-User-ID` или `avatar_id`;
- `403 Forbidden` - пользователь пытается выбрать чужую аватарку;
- `404 Not Found` - пользователь или аватарка не найдены;
- `409 Conflict` - аватарка еще не обработана или уже удалена;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Удаление текущей аватарки пользователя

```http
DELETE /api/v1/avatar
X-User-ID: user-id
```

Ручка удаляет текущую выбранную аватарку пользователя из `X-User-ID`: API делает мягкое удаление записи аватарки, сбрасывает ссылку `app_user.current_avatar_id`, публикует сообщение удаления в RabbitMQ и возвращает `204 No Content`. Физическое удаление исходного изображения и миниатюр из MinIO/S3 выполняется асинхронно воркером.

Если текущая аватарка не выбрана, ручка остается идемпотентной и возвращает `204 No Content`.

Ошибки:

- `400 Bad Request` - некорректный `X-User-ID`;
- `403 Forbidden` - текущая аватарка принадлежит другому пользователю;
- `404 Not Found` - пользователь или текущая аватарка не найдены;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Удаление аватарки по ID

```http
DELETE /api/v1/avatars/{avatar_id}
X-User-ID: user-id
```

Ручка удаляет указанную аватарку пользователя из `X-User-ID`: API делает мягкое удаление записи аватарки, публикует сообщение удаления в RabbitMQ и возвращает `204 No Content`. Если удаляемая аватарка была текущей, API дополнительно сбрасывает ссылку `app_user.current_avatar_id`. Физическое удаление исходного изображения и миниатюр из MinIO/S3 выполняется асинхронно воркером.

Ошибки:

- `400 Bad Request` - некорректный `X-User-ID` или `avatar_id`;
- `403 Forbidden` - пользователь пытается удалить чужую аватарку;
- `404 Not Found` - пользователь или аватарка не найдены;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Проверка жизнеспособности HTTP-сервера

```http
GET /live
```

Ручка не обращается к внешним зависимостям и подтверждает, что процесс запущен и не требует перезапуска.

Успешный ответ:

```json
{
  "status": "ok"
}
```

Успешная проверка возвращает `200 OK`.

### Проверка готовности HTTP-сервера

```http
GET /ready
```

Ручка проверяет внешние зависимости и подтверждает готовность HTTP-сервера принимать пользовательский трафик.

Ответ содержит общий статус HTTP-сервера и состояние зависимостей:

```json
{
  "status": "ok",
  "checks": {
    "postgres": "ok",
    "s3": "ok",
    "rabbitmq": "ok"
  }
}
```

Минимальный набор значений:

- общий `status`: `ok` или `degraded`;
- значения в `checks`: `ok` или `error`.

Если общий статус равен `ok`, API возвращает `200 OK`. Если хотя бы одна зависимость недоступна, тогда общий статус равен `degraded`, и API возвращает `503 Service Unavailable`.

Ручка `GET /health` сохранена для совместимости и полностью повторяет поведение `GET /ready`.

### Проверки состояния воркера

Воркер запускает отдельный HTTP-сервер проверок состояния. Его адрес задаётся настройкой `health_address`.

Доступные ручки:

- `GET /live` подтверждает, что процесс воркера запущен и не требует перезапуска;
- `GET /ready` проверяет доступность PostgreSQL, S3 и готовность RabbitMQ-консьюмера обрабатывать сообщения.

Формат ответов и HTTP-статусы совпадают с одноимёнными ручками основного HTTP-сервера. Сервер проверок состояния
воркера не использует TLS, поскольку предназначен для внутренних Kubernetes-проб, а не для пользовательского трафика.

## Модель безопасности MVP

Полноценная аутентификация в MVP не входит.

Текущая модель:

- TLS отвечает за безопасность соединения между клиентами, включая SPA, и сервером;
- `X-User-ID` считается доверенным заголовком текущего MVP;
- сервер валидирует `X-User-ID` как UUID в ручках, где этот заголовок требуется;
- удаление разрешено только владельцу аватарки;
- email валидируется и нормализуется на сервере;
- сервер не возвращает клиенту внутренние ошибки PostgreSQL, MinIO/S3 или RabbitMQ;
- в репозитории не хранятся реальные секреты: пароль PostgreSQL, ключи MinIO, учетные данные RabbitMQ и приватный ключ TLS.

### TLS

TLS защищает транспортный канал между клиентами, включая SPA, и сервером от чтения и подмены данных. TLS не заменяет аутентификацию, проверку владельца аватарки, валидацию `X-User-ID` и проверку загружаемого файла.

Для локальной разработки предполагается локальный CA и серверный сертификат, подписанный этим CA. Сервер загружает сертификат и приватный ключ из конфигурации:

```yaml
tls_cert: certs/server.crt
tls_key: certs/server.key
```
Для браузера, который открывает SPA, локальный CA должен быть доверенным в локальном окружении. Иначе браузер покажет предупреждение о недоверенном сертификате.

## Ограничения и мотивация лимитов

- Email ограничен 255 символами, потому что это практический верхний предел адреса и поле используется для ручного ввода и поиска.
- Имя файла ограничено 255 символами, потому что это распространенный верхний предел длины имени файла в файловых
  системах;
- MIME-тип может содержать дополнительные параметры, но на практике редко превышает 50-70 символов, поэтому лимит 255
  символов оставляет запас;
- Размер файла ограничен 10 МиБ, чтобы MVP мог принимать файл одним HTTP-запросом `multipart/form-data` без возобновляемой загрузки частями и отдельной политики длительных операций. При таком лимите файл можно целиком читать в память для проверки и обработки, но сервер и воркер должны ограничивать число одновременно обрабатываемых загрузок, чтобы несколько параллельных задач не исчерпали доступную память.
- Размер изображения ограничен `4096x4096` пикселей и `16777216` пикселей суммарно. Это позволяет принимать типичные фотографии с современного телефона, но ограничивает объем памяти после декодирования изображения.
- Ключ объектного хранилища ограничен `VARCHAR(512)`: этого хватает для префиксов, UUID пользователя, UUID аватарки и имени варианта изображения; исходное имя файла в ключ объектного хранилища не включается;
- Миниатюры ограничены размерами `100x100` и `300x300`, потому что этого достаточно для списков, профилей, а также демонстрации асинхронной обработки в этом проекте.

## Конфигурация

Компоненты приложения получают настройки из нескольких источников. Приоритет от меньшего к большему:

```text
дефолтное значение < значение из конфигурационного файла < переменная окружения < флаг командной строки
```

Если переменная окружения задана, она считается явным значением даже при пустой строке. Пустое значение обязательного параметра должно приводить к ошибке конфигурации, а не к откату на нижестоящий источник.

В репозитории должны храниться только примеры конфигурации с заглушками вместо секретов. Реальные локальные конфиги, пароли PostgreSQL, ключи MinIO и учетные данные RabbitMQ не коммитятся.

TLS-пути сервера задаются через конфигурацию, переменные окружения или CLI-флаги с тем же приоритетом источников:

```text
tls_cert
tls_key
```

Для локального запуска эти значения будут указывать на `certs/server.crt` и `certs/server.key`.

## Локальный запуск

Сгенерируйте локальные TLS-сертификаты, если их еще нет:

```bash
./certs/generate-local-certs.sh
```

Создайте локальный env-файл и заполните пустые значения:

```bash
cp .env.example .env
```

Запустите локальный стек:

```bash
make up
```

Команда собирает Docker-образ и запускает:

- Nginx;
- PostgreSQL;
- PostgreSQL Exporter;
- MinIO;
- RabbitMQ;
- OpenTelemetry Collector;
- OpenSearch и OpenSearch Dashboards;
- Prometheus и Grafana;
- Jaeger;
- сервер;
- воркер;
- мигратор базы данных.

Для локальной разработки сервер, воркер и мигратор удобнее запускать через `go run`. Перед этим отдельно поднимите инфраструктуру:

```bash
make infra-up
```

Создайте локальный конфиг сервера по примеру `config/server.local.example.yaml`. Укажите в нем те же учетные данные,
что в `.env`, но используйте `localhost` в адресах PostgreSQL, MinIO и RabbitMQ.

Примените миграции базы данных:

```bash
go run ./cmd/migrate -c config/server.local.yaml
```

Запустите сервер локально:

```bash
go run ./cmd/server -c config/server.local.yaml
```

Создайте локальный конфиг воркера по примеру `config/worker.local.example.yaml` с теми же учетными данными.

Запустите воркер:

```bash
go run ./cmd/worker -c config/worker.local.yaml
```

После запуска состояние воркера можно проверить командами:

```bash
curl http://localhost:3203/live
curl http://localhost:3203/ready
```

Docker-образ приложения можно собрать отдельно, без запуска Docker Compose:

```bash
docker build -f docker/Dockerfile -t goph-profile:local .
```

Dockerfile использует multi-stage build: отдельный build stage на Go-образе и минимальный runtime stage с бинарниками
`server`, `worker` и `migrate`. По умолчанию контейнер запускает `/app/server`; воркер и мигратор запускаются тем же
образом с переопределением entrypoint на `/app/worker` и `/app/migrate` соответственно.

## Наблюдаемость

Сервер и воркер пишут структурированные логи через `slog`. Каждая запись выводится в stdout в формате `logging.format`
(`text` или `json`) и параллельно отправляется по OTLP/gRPC в OpenTelemetry Collector, который сохраняет логи в
OpenSearch. Для локального просмотра логов используется OpenSearch Dashboards.

Сервер и воркер отправляют метрики по OTLP/gRPC в OpenTelemetry Collector, а Prometheus оттуда их забирает.
Сервер пишет метрики пользовательских сценариев и HTTP-запросов. Воркер пишет метрики асинхронной обработки
аватарок и удаления файлов. Оба процесса также отправляют метрики рантайма Go: память, сборку мусора и количество
горутин.
Инфраструктурные метрики СУБД, очередей, объектного хранилища и хоста отдают непосредственно PostgreSQL Exporter,
RabbitMQ, MinIO и Node Exporter.
Grafana автоматически поднимает дашборды из `docker/grafana/dashboards` для сервера, воркера, рантайма Go, PostgreSQL,
RabbitMQ, MinIO и хоста.

Сервер и воркер отправляют трассы по OTLP/gRPC в OpenTelemetry Collector, а он передает их в Jaeger.
Трассировка охватывает HTTP-запросы, публикацию и чтение сообщений RabbitMQ, операции PostgreSQL и операции MinIO/S3.
Контекст трассировки передается от сервера к воркеру через заголовки сообщений RabbitMQ.

Локальные UI для анализа телеметрии:

- Grafana: <http://localhost:3000> — дашборды метрик, просмотр логов через OpenSearch datasource и трасс через Jaeger datasource;
- Prometheus: <http://localhost:9090> — PromQL-запросы и проверка собранных метрик;
- Jaeger: <http://localhost:16686> — поиск и анализ трасс;
- OpenSearch Dashboards: <http://localhost:5601> — просмотр и поиск логов.

### Как проверить наблюдаемость

После запуска локального стека через `make up` выполните небольшой пользовательский сценарий. Он создает HTTP-запросы,
логи сервера, метрики API, сообщение RabbitMQ, обработку воркером, операции PostgreSQL и операции MinIO/S3.
Скрипт использует `curl` и `jq`.

```bash
./scripts/check-observability.sh
```

После этого проверьте телеметрию:

- в Grafana откройте дашборды `GophProfile Server`, `GophProfile Worker`, `GophProfile Go Runtime`, `GophProfile PostgreSQL`,
  `GophProfile RabbitMQ`, `GophProfile MinIO` и `GophProfile Host`;
- в Prometheus выполните запросы `http_server_requests_total`, `avatar_api_actions_total`, `avatar_worker_jobs_total`,
  `up{job="postgres"}`, `up{job="rabbitmq"}`, `up{job="minio"}` и `up{job="node"}`;
- в Jaeger выберите сервис `goph-profile-server` или `goph-profile-worker` и найдите трассы с операциями
  `POST /api/v1/avatars`, `rabbitmq.publish`, `rabbitmq.consume.avatar_processing`, `postgres.avatar.create` и
  `minio.put_object`;
- в OpenSearch Dashboards или в Grafana Explore через datasource `OpenSearch` проверьте логи в индексе `otel-logs-*`.
