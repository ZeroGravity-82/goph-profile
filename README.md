# GophProfile

GophProfile - микросервис для управления аватарками пользователей.

Пользователь загружает свою фотографию один раз, а внешние платформы, например блоги, форумы и сервисы комментариев, могут запросить его аватарку по email. Если пользователь или готовая аватарка не найдены, сервис возвращает стандартное изображение-заглушку.

Сейчас цель - собрать первый рабочий MVP: REST API, PostgreSQL, MinIO/S3, RabbitMQ, воркер асинхронной обработки и Docker Compose для локального окружения.

## Компоненты системы

- HTTP-сервер на Go с REST API и раздачей web-интерфейса;
- воркер на Go для фоновой обработки изображений и удаления файлов;
- PostgreSQL для пользователей, метаданных аватарок и статусов;
- MinIO/S3 для исходных изображений аватарок и миниатюр;
- RabbitMQ для сообщений загрузки, обработки и удаления;
- готовый SPA-интерфейс загрузки, адаптированный под модель email -> user_id.

## Технологический стек

- Go 1.21;
- `chi` для HTTP-роутинга;
- PostgreSQL;
- SQL-миграции через `goose` или совместимый инструмент;
- MinIO как S3-совместимое объектное хранилище;
- RabbitMQ для асинхронной обработки;
- Docker и Docker Compose;
- `slog` для логирования;
- `golangci-lint` для статического анализа;
- `go test`, `testify` и `testcontainers-go` для тестов.

## Текущее состояние реализации

Код проекта еще не начат. Зафиксированы архитектурные решения и модель MVP.

Будет реализовано в MVP:

- REST API для загрузки, чтения, удаления и просмотра метаданных аватарок;

- создание миниатюр `100x100` и `300x300`;

- Dockerfile и Docker Compose для локального запуска.

## Архитектурные решения

### REST API

Основной интерфейс проекта - REST API. Он подходит для готового SPA и внешних сервисов, которым нужно получать аватарки по HTTP.

### Email и внутренний user_id

`email` и `user_id` не смешиваются.

Внутри сервиса пользователь имеет стабильный UUID:

```text
app_user.id -> avatar.user_id
```

Email используется как публичный атрибут для поиска аватарки внешними сервисами. Такой подход позволяет нормализовать email, искать его без учета регистра и не использовать изменяемый пользовательский атрибут как внутренний ключ владения.

SPA работает так:

1. Пользователь вводит email.
2. SPA вызывает `POST /api/v1/users/resolve`.
3. Сервер находит или создает пользователя и возвращает внутренний UUID.
4. SPA загружает аватарку через `POST /api/v1/avatars` с заголовком `X-User-ID: <user_id>`.

В MVP хранится нормализованный email: `trim + lowercase`. Исходный вариант написания email, введенный пользователем, отдельно не хранится, потому что сейчас сервис не показывает email в пользовательском профиле и не отправляет письма. Если позже появится UX-сценарий, где важно сохранить исходное написание, можно добавить отдельное поле.

### Публичное получение аватарки по email

Главный продуктовый сценарий - получить аватарку по email без знания внутреннего UUID:

```http
GET /api/v1/avatar?email=user@example.com
```

Если пользователь или текущая готовая аватарка не найдены, сервис возвращает стандартную PNG-заглушку. Заглушка хранится как статический ресурс:

```text
web/static/default-avatar.png
```

Текущая аватарка выбирается явно. Для этого у пользователя хранится ссылка на текущую аватарку. Публичная выдача по email возвращает выбранную текущую аватарку, только если она имеет статус `ready` и не удалена. Если текущая аватарка не выбрана, еще обрабатывается или удалена, сервис возвращает стандартную заглушку.

Первая успешно обработанная аватарка пользователя становится текущей автоматически, если у пользователя еще нет выбранной текущей аватарки. Последующие загрузки не меняют текущую аватарку без явного выбора пользователя.

### Хранение файлов

PostgreSQL хранит только пользователей, метаданные, статусы и ключи объектного хранилища для аватарок. Оригинальные изображения и миниатюры хранятся только в MinIO/S3.

Это снижает размер базы данных, упрощает раздачу бинарных данных и соответствует назначению объектного хранилища.

### Асинхронная обработка

После загрузки исходного файла аватарки сервер сохраняет метаданные и публикует сообщение в RabbitMQ. Воркер получает сообщение, читает исходное изображение из MinIO/S3, создает миниатюры и обновляет статус аватарки.

RabbitMQ выбран вместо Kafka, потому что в MVP брокер используется как очередь заданий между компонентами одного сервиса: сервер ставит воркеру задачи на обработку изображения или удаление файлов. Здесь важнее подтверждение обработки, повторная доставка и повторные попытки для отдельных заданий, чем долговременный поток сообщений с возможностью повторного воспроизведения.

Параллелизм обработки изображений ограничивается количеством консьюмеров воркера. Это защищает процесс от одновременного декодирования слишком большого числа изображений в память.

Формы сообщений берутся из спецификации и будут уточнены при реализации:

```go
type AvatarUploadMessage struct {
    AvatarID string `json:"avatar_id"`
    UserID   string `json:"user_id"`
    S3Key    string `json:"s3_key"`
}

type AvatarProcessMessage struct {
    AvatarID   string         `json:"avatar_id"`
    Operations []ProcessingOp `json:"operations"`
}

type AvatarDeleteMessage struct {
    AvatarID string   `json:"avatar_id"`
    S3Keys   []string `json:"s3_keys"`
}
```

Удаление тоже выполняется в два шага:

1. API делает мягкое удаление записи аватарки в PostgreSQL и возвращает `204 No Content`.
2. Воркер асинхронно удаляет исходное изображение и миниатюры из MinIO/S3.

Операции воркера должны быть идемпотентными: повторная доставка сообщения не должна ломать состояние и не должна приводить к некорректной ошибке, если объект уже удален. Воркер проверяет текущий статус аватарки перед выполнением операции, а временные ошибки обрабатывает повторными попытками с задержкой между попытками.

## Модель данных

Предварительная схема для MVP:

```text
app_user
- id UUID PRIMARY KEY
- email VARCHAR(255) NOT NULL
- current_avatar_id UUID NULL REFERENCES avatar(id)
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL

avatar
- id UUID PRIMARY KEY
- user_id UUID NOT NULL REFERENCES app_user(id) ON DELETE RESTRICT
- file_name VARCHAR(255) NOT NULL
- mime_type VARCHAR(255) NOT NULL
- size_bytes BIGINT NOT NULL
- width INTEGER NULL
- height INTEGER NULL
- original_object_key VARCHAR(512) NOT NULL
- thumb_100_object_key VARCHAR(512) NULL
- thumb_300_object_key VARCHAR(512) NULL
- status avatar_status NOT NULL
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL
- deleted_at TIMESTAMPTZ NULL
```

Для пользователей нужен уникальный индекс по `email` в таблице `app_user`. Email нормализуется до записи, поэтому `User@Example.com` и `user@example.com` сохраняются как одно и то же значение.

Из-за взаимной ссылки `app_user.current_avatar_id -> avatar.id` и `avatar.user_id -> app_user.id` миграция может сначала создать `app_user` без `current_avatar_id`, затем создать `avatar`, а после этого добавить `current_avatar_id` через `ALTER TABLE`. Текущая аватарка должна принадлежать тому же пользователю, быть в статусе `ready` и не иметь `deleted_at`. Этот инвариант проверяется в usecase выбора текущей аватарки без жесткой защиты на уровне БД.

Статус аватарки хранится в PostgreSQL-перечислении `avatar_status`:

```sql
CREATE TYPE avatar_status AS ENUM (
    'processing',
    'ready',
    'failed',
    'deleting',
    'deleted'
);
```

Назначение статусов:

- `processing` - исходный файл уже загружен, воркер еще не завершил обработку;
- `ready` - аватарка обработана, миниатюры созданы, аватарку можно выдавать клиентам;
- `failed` - обработка завершилась ошибкой, аватарку нельзя выбрать текущей;
- `deleting` - запись аватарки мягко удалена, физическое удаление файлов из MinIO/S3 еще выполняется;
- `deleted` - файлы аватарки удалены из MinIO/S3.

## API

Планируемые API-ручки MVP:

```http
# Пользователь и текущая аватарка:
POST   /api/v1/users/resolve
GET    /api/v1/avatar?email={email}
PATCH  /api/v1/avatar/current

# Операции с конкретной аватаркой по ее ID:
POST   /api/v1/avatars
GET    /api/v1/avatars/{avatar_id}
GET    /api/v1/avatars/{avatar_id}/metadata
DELETE /api/v1/avatars/{avatar_id}

# Операции с аватарками через владельца:
GET    /api/v1/users/{user_id}/avatar
GET    /api/v1/users/{user_id}/avatars
DELETE /api/v1/users/{user_id}/avatar

# Служебные и web-ручки:
GET    /health
GET    /web/upload
POST   /web/upload
GET    /web/gallery/{user_id}
```

GET-ручки публичного чтения не требуют `X-User-ID`. Заголовок `X-User-ID` требуется только для операций, которые меняют состояние от имени пользователя: загрузка, выбор текущей аватарки и удаление.

### Публичное получение текущей аватарки по email

```http
GET /api/v1/avatar?email=user@example.com
```

Успешный ответ возвращает бинарные данные текущей готовой аватарки пользователя:

```http
Content-Type: image/jpeg|image/png|image/webp
Cache-Control: max-age=86400
```

Если пользователь не найден, текущая аватарка не выбрана, еще обрабатывается или удалена, API возвращает `200 OK` со стандартной PNG-заглушкой `web/static/default-avatar.png`.

Ошибки:

- `400 Bad Request` - некорректный или отсутствующий `email`;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Загрузка аватарки

```http
POST /api/v1/avatars
Content-Type: multipart/form-data
X-User-ID: user-id
```

Тело формы:

```text
file: binary image
```

Ограничения:

- максимальный размер файла: 10 МиБ;
- максимальная длина имени файла: 255 байт;
- форматы: JPEG, PNG, WebP;
- MIME-тип и содержимое файла должны проверяться на сервере.

Успешный ответ:

Ответ содержит ID созданной аватарки, владельца, URL для получения аватарки, статус обработки и момент создания записи.

```json
{
  "id": "avatar-id",
  "user_id": "user-id",
  "url": "/api/v1/avatars/avatar-id",
  "status": "processing",
  "created_at": "2026-07-14T00:00:00Z"
}
```

Ошибки:

- `400 Bad Request` - некорректный `X-User-ID`, отсутствующий файл, слишком длинное имя файла или неподдерживаемый формат;
- `413 Payload Too Large` - файл больше 10 МиБ;
- `415 Unsupported Media Type` - `Content-Type` не `multipart/form-data`;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Получение аватарки

```http
GET /api/v1/avatars/{avatar_id}?size=300x300&format=png
```

Параметры:

- `size`: `100x100`, `300x300`, `original`;
- `format`: `jpeg`, `png`, `webp`.

Параметр `format` не выполняет конвертацию. Если он задан, запрошенный формат должен совпадать с фактическим форматом возвращаемого объекта. Если формат не совпадает с выбранным объектом, API возвращает `400 Bad Request`. Оригинал сохраняет исходный MIME-тип, миниатюры MVP отдаются как PNG.

Успешный ответ возвращает бинарные данные изображения и заголовки:

```http
Content-Type: image/jpeg|image/png|image/webp
Cache-Control: max-age=86400
```

Если аватарка по ID не найдена, API возвращает `404` с JSON-ошибкой.

### Метаданные аватарки

```http
GET /api/v1/avatars/{avatar_id}/metadata
```

Ответ содержит ID, владельца, имя файла, MIME-тип, размер файла в байтах, размер изображения в пикселях, список доступных миниатюр, моменты создания и обновления аватарки.

Пример ответа:

```json
{
  "id": "avatar-id",
  "user_id": "user-id",
  "file_name": "avatar.jpg",
  "mime_type": "image/jpeg",
  "size_bytes": 1024000,
  "width": 1920,
  "height": 1080,
  "status": "ready",
  "thumbnails": [
    {
      "size": "100x100",
      "url": "/api/v1/avatars/avatar-id?size=100x100"
    },
    {
      "size": "300x300",
      "url": "/api/v1/avatars/avatar-id?size=300x300"
    }
  ],
  "created_at": "2026-07-14T00:00:00Z",
  "updated_at": "2026-07-14T00:00:05Z"
}
```

Ошибки:

- `400 Bad Request` - некорректный `avatar_id`;
- `404 Not Found` - аватарка не найдена;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Выбор текущей аватарки

```http
PATCH /api/v1/avatar/current
Content-Type: application/json
X-User-ID: user-id
```

Тело запроса:

```json
{
  "avatar_id": "avatar-id"
}
```

Ручка выбирает готовую аватарку пользователя как текущую. Пользователь определяется по `X-User-ID`. Выбранная аватарка должна принадлежать этому пользователю, иметь статус `ready` и не иметь `deleted_at`.

Успешный ответ:

```http
204 No Content
```

Ошибки:

- `400 Bad Request` - некорректный `X-User-ID` или `avatar_id`;
- `403 Forbidden` - пользователь пытается выбрать чужую аватарку;
- `404 Not Found` - пользователь или аватарка не найдены;
- `409 Conflict` - аватарка еще не обработана или уже удалена;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Удаление текущей аватарки пользователя

```http
DELETE /api/v1/users/{user_id}/avatar
X-User-ID: user-id
```

Ручка удаляет текущую выбранную аватарку пользователя: API делает мягкое удаление записи аватарки, сбрасывает ссылку `app_user.current_avatar_id` и возвращает `204 No Content`. Физическое удаление исходного изображения и миниатюр из MinIO/S3 выполняется асинхронно воркером.

Если текущая аватарка не выбрана, ручка остается идемпотентной и возвращает `204 No Content`.

Ошибки:

- `400 Bad Request` - некорректный `user_id` или `X-User-ID`;
- `403 Forbidden` - `X-User-ID` не совпадает с пользователем из пути;
- `404 Not Found` - пользователь не найден;
- `500 Internal Server Error` - внутренняя ошибка без раскрытия деталей инфраструктуры.

### Определение пользователя по email

```http
POST /api/v1/users/resolve
Content-Type: application/json
```

```json
{
  "email": "user@example.com"
}
```

Ответ:

Ответ содержит внутренний `user_id` пользователя и нормализованный email.

```json
{
  "user_id": "user-id",
  "email": "user@example.com"
}
```

### Healthcheck

```http
GET /health
```

Ответ должен быть JSON-объектом с общим статусом сервиса и состоянием зависимостей:

```json
{
  "status": "ok",
  "checks": {
    "postgres": "ok",
    "s3": "ok",
    "rabbitmq": "ok"
  }
}
```

Минимальный набор значений:

- общий `status`: `ok` или `degraded`;
- значения в `checks`: `ok` или `error`.

Если общий статус равен `ok`, API возвращает `200 OK`. Если хотя бы одна зависимость недоступна, тогда общий статус равен `degraded`, и API возвращает `503 Service Unavailable`.

## Модель безопасности MVP

Полноценная аутентификация в MVP не входит.

Текущая модель:

- TLS отвечает за безопасность соединения между клиентами, включая SPA, и сервером;
- `X-User-ID` считается доверенным заголовком текущего MVP;
- сервер валидирует `X-User-ID` как UUID в ручках, где этот заголовок требуется;
- удаление разрешено только владельцу аватарки;
- email валидируется и нормализуется на сервере;
- сервер не возвращает клиенту внутренние ошибки PostgreSQL, MinIO/S3 или RabbitMQ;
- в репозитории не хранятся реальные секреты: пароль PostgreSQL, ключи MinIO, учетные данные RabbitMQ и приватный ключ TLS.

### TLS

TLS защищает транспортный канал между клиентами, включая SPA, и сервером от чтения и подмены данных. TLS не заменяет аутентификацию, проверку владельца аватарки, валидацию `X-User-ID` и проверку загружаемого файла.

Для локальной разработки предполагается локальный CA и серверный сертификат, подписанный этим CA. Сервер загружает сертификат и приватный ключ из конфигурации:

```yaml
tls_cert: certs/server.crt
tls_key: certs/server.key
```
Для браузера, который открывает SPA, локальный CA должен быть доверенным в локальном окружении. Иначе браузер покажет предупреждение о недоверенном сертификате.

## Ограничения и мотивация лимитов

- Email ограничен 255 символами, потому что это практический верхний предел адреса и поле используется для ручного ввода и поиска.
- Имя файла ограничено 255 символами, потому что это распространенный верхний предел длины имени файла в файловых
  системах;
- MIME-тип может содержать дополнительные параметры, но на практике редко превышает 50-70 символов, поэтому лимит 255
  символов оставляет запас;
- Размер файла ограничен 10 МиБ, чтобы MVP мог принимать файл одним HTTP-запросом `multipart/form-data` без возобновляемой загрузки частями и отдельной политики длительных операций. При таком лимите файл можно целиком читать в память для проверки и обработки, но сервер и воркер должны ограничивать число одновременно обрабатываемых загрузок, чтобы несколько параллельных задач не исчерпали доступную память.
- Размер изображения ограничен `4096x4096` пикселей и `16777216` пикселей суммарно. Это позволяет принимать типичные фотографии с современного телефона, но ограничивает объем памяти после декодирования изображения.
- Ключ объектного хранилища ограничен `VARCHAR(512)`: этого хватает для префиксов, UUID пользователя, UUID аватарки и имени варианта изображения; исходное имя файла в ключ объектного хранилища не включается;
- Миниатюры ограничены размерами `100x100` и `300x300`, потому что этого достаточно для списков, профилей, а также демонстрации асинхронной обработки в этом проекте.

## Конфигурация

Приложение должно получать настройки из нескольких источников. Приоритет от меньшего к большему:

```text
дефолтное значение < значение из конфигурационного файла < переменная окружения < флаг командной строки
```

Если переменная окружения задана, она считается явным значением даже при пустой строке. Пустое значение обязательного параметра должно приводить к ошибке конфигурации, а не к откату на нижестоящий источник.

В репозитории должны храниться только примеры конфигурации с заглушками вместо секретов. Реальные локальные конфиги, пароли PostgreSQL, ключи MinIO и учетные данные RabbitMQ не коммитятся.

TLS-пути сервера задаются через конфигурацию, переменные окружения или CLI-флаги с тем же приоритетом источников:

```text
tls_cert
tls_key
```

Для локального запуска эти значения будут указывать на `certs/server.crt` и `certs/server.key`.

## Локальный запуск

Команды будут уточнены после создания кода, Makefile и compose-файлов.

Локальный сценарий после появления кода и скрипта генерации сертификатов будет следующим:

```bash
./certs/generate-local-certs.sh
make up
make test
make lint
go run ./cmd/server -c config/server.local.yaml
go run ./cmd/worker -c config/worker.local.yaml
```

Локальная инфраструктура MVP:

- PostgreSQL;
- MinIO;
- RabbitMQ;
- server;
- воркер.

Dockerfile должен быть multi-stage: отдельный build stage на Go-образе и минимальный runtime stage с бинарниками `server` и `worker`. Web-ресурсы копируются в runtime-образ рядом с `server`; их использует только HTTP-сервер для раздачи SPA и `default-avatar.png`.

## Тестирование

Минимальные проверки после реализации:

```bash
go test ./...
golangci-lint run
```

Интеграционные тесты, которым нужны PostgreSQL, MinIO или RabbitMQ, должны запускаться отдельной командой или с build tag `integration`:

```bash
go test -tags=integration ./...
```

Для изолированного тестового окружения используется `testcontainers-go`, если тесту нужен реальный PostgreSQL, MinIO или RabbitMQ.

Целевое покрытие тестами для MVP - больше 50%. Способ расчета покрытия нужно уточнить после появления структуры пакетов.

Приоритет покрытия:

1. usecase-сценарии;
2. HTTP-хендлеры: валидация и маппинг ошибок;
3. репозитории PostgreSQL;
4. адаптеры S3 и RabbitMQ;
5. проверка и обработка изображений.

## Чек-лист перед ревью

Перед отправкой проекта на ревью должны быть выполнены все пункты:

- все API-ручки реализованы и работают корректно;
- web-интерфейс позволяет загружать, просматривать и удалять аватарки;
- асинхронная обработка через RabbitMQ работает;
- обработка сообщений идемпотентна;
- файлы сохраняются в MinIO/S3, а метаданные - в PostgreSQL;
- покрытие unit-тестами больше 50%;
- `golangci-lint run` проходит без ошибок;
- архитектура следует принципам Clean Architecture;
- ошибки обрабатываются корректно и не раскрывают внутренние детали инфраструктуры;
- Dockerfile сделан как оптимизированный multi-stage build;
- Docker Compose для локальной разработки работает;
- Docker-образы собираются и запускаются без ошибок.

## Структура папок

Ожидаемая структура после реализации:

```text
cmd/server/                  # точка входа HTTP-сервера
cmd/worker/                  # точка входа воркера
config/                      # примеры конфигурации без секретов
certs/                       # TLS-сертификаты для локального запуска и разработки
internal/app/server/         # сборка зависимостей сервера
internal/app/worker/         # сборка зависимостей воркера
internal/buildinfo/          # версия и дата сборки бинарных файлов
internal/config/             # конфигурация клиента и сервера
internal/domain/model/       # доменные модели, типы и ошибки
internal/image/              # проверка и обработка изображений
internal/logging/            # настройка логирования
internal/queue/rabbitmq/     # публикация и получение сообщений RabbitMQ
internal/storage/minio/      # S3-совместимое хранилище файлов аватарок
internal/storage/postgres/   # реализация хранения данных в PostgreSQL
internal/httpserver/         # HTTP-сервер, роутер, middleware и REST-хендлеры
internal/usecase/            # сценарии использования приложения и минимальные интерфейсы их зависимостей
migrations/                  # SQL-миграции базы данных
web/static/                  # SPA-ресурсы и default-avatar.png
```
